# 站内消息推送流

本文梳理当前项目中“站内消息”的后端触发、入库、前端拉取与已读处理流程，便于后续扩展消息类型。

## 1. 数据模型

- 表模型：`model/message.go` 中 `Message`
- 核心字段：
  - `user_id`：消息接收人（按账号维度）
  - `type`：消息类型（`system/reservation/borrow/overdue/fine`）
  - `title`、`content`
  - `is_read`、`read_at`
  - `related_id`、`related_type`（用于跳转关联业务）

## 2. 后端统一发送入口

- 服务：`service/message_service.go`
- 统一创建方法：`CreateMessage(userID, msgType, title, content, relatedID, relatedType)`
- 业务快捷方法：`SendReservationAvailableMessage(...)`

说明：业务模块应尽量通过 `MessageService` 发消息，不直接操作 `messages` 表。

## 3. 当前已接入的消息触发点

### 3.1 预约可取书通知（reservation）

- 触发位置：`service/reservation_service.go` -> `ProcessReservationQueue`
- 触发条件：预约状态从 `pending` 变为 `available`
- 发送内容：`📚 预约图书已可借阅`，附取书时限天数
- 关联信息：`related_id=reservationID`，`related_type=reservation`

### 3.2 逾期提醒（overdue）

- 触发位置：`service/borrow_service.go` -> `CheckOverdueRecords`
- 触发方式：定时任务调用（见 `initialize/cron.go`，每小时）
- 发送内容：`⚠️ 图书已逾期`，按秒/分钟/天生成逾期文案
- 关联信息：`related_id=borrowRecordID`，`related_type=borrow`

### 3.3 黑名单通知（system）

- 触发位置：`service/blacklist_service.go`
  - `AddToBlacklist`：拉黑时发送“账户借阅权限已停用”，包含原因与说明
  - `RemoveActiveBlacklistByUserID`：解禁时发送“黑名单已解除”
- 类型：`system`
- 关联：`related_type=blacklist`（`related_id` 当前为空）

## 4. 定时任务与消息关系

`initialize/cron.go` 中与消息相关的任务：

- 每小时：`borrowService.CheckOverdueRecords()` -> 可能发送逾期消息
- 每小时：`reservationService.CheckExpiredReservations()` -> 预约流转（可间接触发后续通知）
- 每天 2:00：自动拉黑逾期严重读者 -> 拉黑消息
- 每天 3:00：检查过期黑名单 -> 当前仅状态恢复，未额外发消息

## 5. 消息 API（后端）

路由定义：`router/message.go`（均需 JWT）

- `GET /message/getMessages`：分页消息列表
- `GET /message/getUnreadCount`：未读数
- `PUT /message/read/:id`：单条已读
- `PUT /message/readAll`：全部已读
- `DELETE /message/delete/:id`：删除消息

控制器：`api/v1/message.go`

## 6. 前端消费流程

主要页面：`web/src/views/BookList.vue` 顶部消息下拉框

- 页面挂载时：
  - `fetchUnreadCount()` 拉未读数
  - 启动轮询 `startUnreadPolling()`：每 15 秒调用一次 `GET /message/getUnreadCount`
- 打开消息面板时：
  - `fetchMessages()` 拉消息列表
- 用户点击消息：
  1. 若未读，先调用 `handleMarkRead` -> `PUT /message/read/:id`
  2. 再按类型跳转：
     - `reservation` 且有 `related_id`：尝试定位相关图书
     - 其他类型：跳转借阅视图
- “全部已读”：
  - `PUT /message/readAll`

### 6.1 轮询方案的性能说明（当前实现）

- 当前策略：**短轮询**（15 秒一次，仅拉未读数量）,代码如下：（BookList.vue）
   ```go
      const startUnreadPolling = () => {
      if (unreadPollingTimer) return
      unreadPollingTimer = setInterval(() => {
        // 页面不可见时不轮询，减少无意义请求
        if (document.hidden) return
        fetchUnreadCount()
      }, 15000)
    }
   ```
- 性能影响评估：
  - 单用户每分钟约 4 次请求，接口开销低（仅 count 查询）
  - 已在前端做页面可见性判断（`document.hidden` 时跳过）
  - 对中小规模并发通常可接受，优点是实现简单、稳定、易排障
- 代价：
  - 不是实时，最坏延迟接近轮询间隔（约 0~15 秒）
  - 用户规模很大时，会有持续的“无效请求”背景流量

### 6.2 WebSocket / SSE 对比

- WebSocket：
  - 优点：双向通信、接近实时，适合后续做更丰富的在线交互
  - 成本：需要连接管理、心跳、断线重连、权限校验、横向扩容（多实例广播）
  - 复杂度：最高
- SSE（Server-Sent Events）：
  - 优点：服务端单向推送，协议简单，天然适合“消息通知”场景
  - 成本：仍需长连接管理、重连与鉴权，代理/网关超时策略要配置
  - 复杂度：中等（一般低于 WebSocket）
- 轮询：
  - 优点：实现最简单，兼容性好
  - 缺点：请求有冗余，实时性受轮询间隔限制

### 6.3 建议

- 当前阶段（本项目现状）：保持 15 秒轮询，优先保证稳定性与维护成本。
- 当出现以下信号时，考虑升级 SSE/WebSocket：
  - 在线用户量明显上升，轮询请求占比偏高
  - 业务需要“秒级实时”提醒
  - 需要服务端主动推送更多事件（不仅未读数）

## 7. 当前注意事项

- 消息接收对象是 `user_id`，不是 `reader_id`。
- 黑名单属于借阅域状态，但通知同样发到账号域消息中心。
- 目前“查看更多消息”在前端为占位（`功能开发中...`），可后续补分页加载。
