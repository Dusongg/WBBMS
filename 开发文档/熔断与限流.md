# Golang 熔断与限流 —— 从本项目的代码实现学起

本文从 **bookadmin** 项目的实际代码出发，说明**限流（Rate Limiting）**和**熔断（Circuit Breaker）**要解决什么问题、核心概念是什么，以及在本项目中是如何实现和接入的。风格与《分布式链路追踪》一致，便于你从代码实现反推原理。

---

## 一、为什么需要限流和熔断？

### 1.1 限流（Rate Limiting）

- **问题**：接口被恶意刷量或突发流量打满，导致响应变慢、甚至雪崩，正常用户也受影响。
- **目标**：在入口控制“每秒/每客户端最多通过多少请求”，超出部分直接拒绝（如 429），保护后端和依赖。
- **典型场景**：登录/注册防暴力尝试、公开 API 防爬、全局限流防止单机过载。

### 1.2 熔断（Circuit Breaker）

- **问题**：当依赖（如 MySQL、Redis）持续失败或超时时，若每个请求仍去访问，会拖垮线程/连接、放大故障。
- **目标**：检测到“失败次数超过阈值”后，**暂时不再调用依赖**（熔断打开），直接快速失败（如 503），给依赖恢复时间；过一段时间再放少量请求试探（半开），成功则恢复（闭合）。
- **典型场景**：Redis 宕机时避免每个请求都去连 Redis 等超时；下游服务不可用时快速失败，避免级联雪崩。

二者配合：**限流在入口控量，熔断在依赖故障时快速失败**，都是提升**稳定性**和可观测性的手段。

---

## 二、本项目的整体架构

- **限流**：HTTP 入口处用 **Token Bucket（令牌桶）** 做全局限流或按 IP 限流，超出返回 **429**。
- **熔断**：对 **MySQL** 和 **Redis** 各有一个熔断器；Redis 的每次命令通过 **redis.Hook** 自动经过熔断器；当熔断打开时，**中间件** 直接返回 **503**，业务不再访问已熔断的依赖。

配置在 `config` 的 `resilience` 下，对应 `config.yaml` 中的 `resilience.rate-limit` 与 `resilience.circuit-breaker`。

---

## 三、限流：概念与代码实现

### 3.1 令牌桶（Token Bucket）简述

- 有一个桶，容量为 **Burst**，按固定速率 **RPS**（每秒）往桶里放令牌。
- 每个请求要消耗 1 个令牌：有令牌则放行，没有则拒绝。
- **RPS** 控制长期平均速率；**Burst** 允许短时突发（例如刚启动时连续几个请求仍可通过）。

本项目使用标准库 `golang.org/x/time/rate` 的 `rate.Limiter` 实现令牌桶。

### 3.2 配置含义

`config/config.go` 中：

```go
type RateLimitConfig struct {
    Enabled bool `yaml:"enabled"`
    RPS     int  `yaml:"rps"`     // 每秒请求数（令牌补充速率）
    Burst   int  `yaml:"burst"`   // 桶容量（短时突发上限）
    PerIP   bool `yaml:"per-ip"`  // 是否按 IP 限流
}
```

- **RPS=100, Burst=50**：平均每秒最多 100 个请求，同时允许最多 50 个“瞬时突发”（例如 0.1 秒内 50 个请求都通过，之后要等令牌补充）。
- **PerIP=true**：每个客户端 IP 单独一个 Limiter，互不影响；**PerIP=false**：全局限流，所有 IP 共用一个桶。

### 3.3 代码实现：`middleware/rate_limit.go`

```go
// 未启用或配置缺失时，中间件直接放行
if global.GVA_CONFIG == nil || !global.GVA_CONFIG.Resilience.RateLimit.Enabled {
    return func(c *gin.Context) { c.Next() }
}

rps := rate.Limit(cfg.RPS)   // 令牌补充速率
burst := cfg.Burst           // 桶容量
globalLimiter := rate.NewLimiter(rps, burst)

// PerIP 时按 c.ClientIP() 取/建 per-IP 的 Limiter（带 sync.RWMutex 的 map）
getLimiter := func(key string) *rate.Limiter { ... }

// 每个请求
limiter := getLimiter(c.ClientIP())  // 或 globalLimiter
if !limiter.Allow() {
    c.AbortWithStatusJSON(429, gin.H{"code": 429, "msg": "请求过于频繁，请稍后再试"})
    return
}
c.Next()
```

要点：

- **Allow()**：非阻塞，有令牌就扣 1 并返回 true，没有则返回 false；不等待令牌，适合 HTTP 快速拒绝。
- **跳过路径**：`/healthz`、`/readyz`、`/metrics`、`/api/healthz`、`/api/readyz` 不限流，避免探针被限流影响就绪判断。

### 3.4 接入位置

`router/router.go` 中，在 `RequestContext` 之后、`CORS` 之前：

```go
if global.GVA_CONFIG != nil && global.GVA_CONFIG.Resilience.RateLimit.Enabled {
    Router.Use(middleware.RateLimit())
}
```

即：**先限流，再走业务**；被限流的请求不会进入后续中间件和 Handler。

## 四、熔断：概念与代码实现

### 4.1 熔断器三态


| 状态                | 含义  | 行为                                                         |
| ----------------- | --- | ---------------------------------------------------------- |
| **Closed（闭合）**    | 正常  | 请求正常通过，并统计成功/失败                                            |
| **Open（打开）**      | 已熔断 | 不再调用依赖，直接返回错误（本项目在 HTTP 层统一返回 503）                         |
| **Half-Open（半开）** | 试探  | 经过 Timeout 后，允许少量请求（MaxRequests）通过，成功则回到 Closed，失败则回到 Open |


本项目使用 [sony/gobreaker](https://github.com/sony/gobreaker)：在**统计窗口 Interval** 内，若**连续失败或总失败数**达到 **FailureThreshold**，则 **ReadyToTrip** 为 true，熔断器变为 Open；**Timeout** 后进入 Half-Open，最多放行 **MaxRequests** 个探测请求。

### 4.2 配置含义

`config/config.go` 中：

```go
type CircuitBreakerConfig struct {
    Enabled          bool `yaml:"enabled"`
    MaxRequests      int  `yaml:"max-requests"`       // 半开状态允许的探测请求数
    Interval         int  `yaml:"interval"`         // 统计窗口（秒）
    Timeout          int  `yaml:"timeout"`           // 熔断后多久进入半开（秒）
    FailureThreshold int  `yaml:"failure-threshold"` // 失败次数阈值，达到即熔断
}
```

- **Interval=10, FailureThreshold=5**：在 10 秒内，连续失败 5 次或总失败 5 次 → 熔断打开。
- **Timeout=30**：打开 30 秒后进入半开。
- **MaxRequests=3**：半开时最多 3 个请求去试探；若都成功则闭合，若有失败则再次打开。

### 4.3 熔断器初始化与使用：`resilience/breaker.go`

- **初始化**：`main.go` 在加载配置后调用 `resilience.InitBreakers()`，根据 `Resilience.CircuitBreaker.Enabled` 创建 **dbBreaker** 和 **redisBreaker**（gobreaker.CircuitBreaker）。
- **执行闭包**：
  - `resilience.DBExecute(fn func() (interface{}, error))`：若熔断器未启用则直接执行 `fn()`；否则通过 `dbBreaker.Execute(fn)` 执行，熔断打开时 gobreaker 会直接返回 ErrOpen，不再执行 `fn`。
  - `resilience.RedisExecute(fn)`：同理，走 redisBreaker。

也就是说：**所有需要熔断保护的“一次依赖调用”都要包在 `DBExecute` / `RedisExecute` 里**。

### 4.4 Redis 自动走熔断：`resilience/redis_hook.go`

Redis 的每次命令如果都手写 `RedisExecute` 会侵入业务，因此用 **redis.Hook** 统一包裹：

```go
func (h *redisBreakerHook) ProcessHook(next redis.ProcessHook) redis.ProcessHook {
    return func(ctx context.Context, cmd redis.Cmder) error {
        _, err := RedisExecute(func() (interface{}, error) {
            return nil, next(ctx, cmd)
        })
        return err
    }
}
```

- **ProcessHook**：单条命令（Get、Set、XRead 等）执行前都会先经 `RedisExecute`，熔断打开时 `RedisExecute` 返回 ErrOpen，不再执行 `next`。
- **ProcessPipelineHook**：Pipeline 整批命令同样被包在 `RedisExecute` 里，整批算一次“调用”。

Hook 的挂载在 `initialize/redis.go`：当 `resilience.RedisBreakerEnabled()` 为 true 时，`client.AddHook(resilience.NewRedisBreakerHook())`。因此 **所有通过该 Redis 客户端的命令都会自动经过 Redis 熔断器**。

### 4.5 DB 熔断器的使用方式

当前项目里 **MySQL 没有类似 GORM 的全局 Hook**，因此：

- **已接入**：`router/router.go` 的 **readyz** 探针里，对 `sqlDB.PingContext` 和 `global.GVA_REDIS.Ping` 分别用 `resilience.DBExecute` / `resilience.RedisExecute` 包裹，这样探针本身会受熔断影响（熔断打开时 Ping 也会失败，readyz 可返回 503）。
- **业务 SQL**：普通业务用的是 `global.DB(ctx).Find(...)` 等，**没有**包在 `DBExecute` 里，因此当前**只有 Redis 在业务路径上被熔断保护**；若希望关键 DB 调用也熔断，可在该调用外手动包一层 `resilience.DBExecute(func() (interface{}, error) { ... })`，或后续为 GORM 增加类似 Hook。

文档中说明现状，便于你理解“熔断保护的是谁”。

### 4.6 HTTP 层快速返回 503：`middleware/circuit_breaker.go`

即使熔断器打开，若业务仍去调 Redis/DB，会得到 gobreaker 的 ErrOpen；为减少无效调用、统一体验，在 **入口** 就检查熔断状态：

```go
if resilience.DBState() == gobreaker.StateOpen || resilience.RedisState() == gobreaker.StateOpen {
    c.AbortWithStatusJSON(503, gin.H{"code": 503, "msg": "服务暂时不可用，请稍后重试"})
    return
}
```

- **顺序**：在 `router` 里先 **RateLimit** 再 **CircuitBreaker**，再 CORS、业务。即：先限流，再看熔断，熔断打开则直接 503，不再进业务逻辑。
- **跳过路径**：`/healthz`、`/readyz`、`/metrics`、`/api/healthz`、`/api/readyz` 不检查熔断，保证探针仍可访问。

## 五、配置与环境变量

`config.yaml` 示例：

```yaml
resilience:
  rate-limit:
    enabled: true
    rps: 100
    burst: 50
    per-ip: true
  circuit-breaker:
    enabled: true
    max-requests: 3
    interval: 10
    timeout: 30
```

环境变量（见 `config/config.go` 的 `applyEnvOverrides`）：

- 限流：`RATE_LIMIT_ENABLED`、`RATE_LIMIT_RPS`、`RATE_LIMIT_BURST`、`RATE_LIMIT_PER_IP`

## 六、调用顺序小结

一次请求在路由上的顺序可以概括为：

1. **Recovery / 头信息**（如 X-Instance-ID、Tracing）
2. **RequestContext**（生成 request_id、写日志、打 Metrics）
3. **RateLimit**：超过限流 → **429**，不再往后走
4. **CircuitBreaker**：DB 或 Redis 熔断打开 → **503**，不再往后走
5. **CORS** → 业务 Handler

业务内：

- 所有 **Redis** 调用：经 `redis.Hook` 自动走 **RedisExecute**，受 Redis 熔断器保护。
- **DB**：readyz 的 Ping 走 **DBExecute**；普通业务 SQL 当前未包熔断，可按需在关键路径使用 **DBExecute**。

## 七、如何验证与学习

1. **限流**：将 `rps` 设为较小值（如 2），`per-ip: true`，用浏览器或 curl 快速连续请求同一接口，应很快收到 429；观察响应体与日志。
2. **熔断**：将 Redis 停掉或配错地址，持续触发会访问 Redis 的接口，在达到 `failure-threshold` 后，应开始收到 503；恢复 Redis 并等待 `timeout` 进入半开，再请求可逐渐恢复。
3. **与链路追踪结合**：429/503 的请求也会经过 Tracing；在 Jaeger 中可按 trace_id 看该请求在限流/熔断前的部分调用（若有）。

**一键验证脚本**：`./scripts/verify_resilience.sh`（需全栈已启动，BASE_URL 默认 [http://localhost）。](http://localhost）。)

## 八、小结表


| 能力       | 本项目实现                                              | 你要记住的                                                |
| -------- | -------------------------------------------------- | ---------------------------------------------------- |
| 限流算法     | Token Bucket（`golang.org/x/time/rate`）             | RPS=速率，Burst=突发；PerIP 按 IP 分桶                        |
| 限流位置     | Gin 中间件，在业务前执行                                     | 超限直接 429，健康/就绪/指标路径跳过                                |
| 熔断库      | sony/gobreaker                                     | Closed → Open（失败超阈值）→ Half-Open（Timeout 后试探）→ Closed |
| Redis 熔断 | redis.Hook 包裹每条命令/每批 Pipeline                      | 无需业务手写，所有 Redis 调用自动经熔断                              |
| DB 熔断    | InitBreakers 创建 dbBreaker；readyz 用 DBExecute(Ping) | 业务 SQL 未统一包熔断，可按需对关键调用包 DBExecute                    |
| HTTP 层   | CircuitBreaker 中间件查 DB/Redis 状态                    | 任一侧 Open 即 503，健康探针路径跳过                              |


这样，你就从代码实现上把本项目的**熔断与限流**串起来了；若要扩展（例如按用户 ID 限流、或为 GORM 加熔断 Hook），可以在现有中间件和 `resilience` 包上继续迭代。
