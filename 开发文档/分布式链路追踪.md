# Golang 分布式链路追踪 —— 从本项目的代码实现学起

本文从 **bookadmin** 项目的实际代码出发，说明什么是分布式链路追踪、为什么需要它，以及在本项目中是如何实现的。适合在已有 HTTP/GORM/Redis 经验的基础上，系统学习 OpenTelemetry 在 Go 中的落地方式。

---

## 一、什么是分布式链路追踪？

### 1.1 问题场景

一次「获取分类列表」的请求，背后可能经过：

- **HTTP**：进入 Gin 路由
- **中间件**：JWT、CORS、RequestContext
- **Handler**：解析参数、调 Service
- **Service**：业务逻辑、可能调多个依赖
- **GORM**：多次 SQL 查询
- **Redis**：缓存或 Stream 消费

当接口变慢或报错时，仅靠「请求 ID + 日志」很难回答：

- 时间主要耗在**哪一层**（HTTP / DB / Redis）？
- **哪几条 SQL** 或 **哪几次 Redis 命令**属于这一次请求？
- 如果将来拆成多个服务（借阅服务、用户服务），**一次用户操作**会跨多个进程，如何串成一条线？

**分布式链路追踪** 要解决的就是：**为一次请求生成一个全局唯一的 Trace，并在各个组件（甚至多个服务）中把同一 Trace 下的所有操作记录成一条“调用链”**，便于定位延迟和错误。

### 1.2 核心概念（对应到本项目）


| 概念             | 含义                       | 在本项目中的体现                                               |
| -------------- | ------------------------ | ------------------------------------------------------ |
| **Trace**      | 一次完整请求的整条调用链             | 例如一次 `GET /api/category` 从进入到返回                        |
| **TraceID**    | 该链路的全局唯一 ID              | 响应头 `X-Trace-ID`，在 Jaeger 里用其查询整条链                     |
| **Span**       | 链路上的一个“节点”（一次操作）         | 如：HTTP 请求、GORM 某次查询、Redis 某次命令                         |
| **Span 父子关系**  | 谁调用了谁                    | HTTP Span → 业务 Span → GORM Span，形成树状结构                 |
| **Context 传播** | 把 TraceID/SpanID 沿调用链往下传 | 用 `context.Context` 在 Handler → Service → DB/Redis 间传递 |


整条链在「采集端」汇总后，发送到 **Jaeger**（或其它支持 OTLP 的后端），就可以按 TraceID 查一次请求下的所有 Span、耗时分布。

## 二、本项目的技术选型与整体架构

- **标准**： [OpenTelemetry](https://opentelemetry.io/)（业界标准，与具体后端解耦）
- **导出协议**： OTLP over gRPC（`localhost:4317`）
- **后端**： 任意支持 OTLP 的后端（如 Jaeger、Grafana Tempo），配置里通过 `tracing.endpoint` 指定

数据流可以概括为：

```
HTTP 请求
  → Gin (otelgin) 为请求创建 Root Span，并把 Trace 信息放入 context
  → Handler 使用 c.Request.Context() 调 Service / global.DB(ctx)
  → GORM (otelgorm) / Redis (redisotel) 从 context 取出 Trace 信息，创建子 Span
  → 所有 Span 由 OpenTelemetry SDK 批量发送到 OTLP 后端（如 Jaeger）
```

**配置开关**：`config/config.go` 中的 `TracingConfig`：

```yaml
tracing:
  enabled: true
  endpoint: "localhost:4317"   # OTLP gRPC
  service: "bookadmin-api"     # 在 Jaeger 里显示的服务名
```

`main.go` 在 API 模式下会先调用 `observability.InitTracer()`，再初始化 GORM，这样 GORM 的 otel 插件才能生效。

## 三、代码实现拆解

### 3.1 初始化 Tracer：`observability/tracing.go`

```go
// 使用 OTLP gRPC 导出到 Jaeger 等
exporter, err := otlptracegrpc.New(ctx,
    otlptracegrpc.WithInsecure(),  //不使用 TLS
    otlptracegrpc.WithEndpoint(endpoint),
)

tracerProvider = sdktrace.NewTracerProvider(
    sdktrace.WithBatcher(exporter),
    sdktrace.WithResource(resource.NewWithAttributes(..., semconv.ServiceNameKey.String(serviceName))),
    sdktrace.WithSampler(sdktrace.AlwaysSample()),   //100%采样
)
otel.SetTracerProvider(tracerProvider)
otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(
    propagation.TraceContext{},  // 跨进程时把 trace 信息放进 HTTP Header
    propagation.Baggage{},
))
```

要点：

- **TracerProvider**：负责创建 Tracer、采样、导出。
- **TextMapPropagator**：将来若有 HTTP/gRPC 调用其它服务，会把 TraceID/SpanID 注入到 Header，实现跨服务链路串联。
- **Sampler**：当前 `AlwaysSample()` 表示全量采样；生产可按比例或按错误采样以控制成本。

### 3.2 HTTP 入口：Gin + otelgin

`router/router.go` 中：

```go
if observability.TracerEnabled() {
    Router.Use(otelgin.Middleware("bookadmin-api"))
    Router.Use(traceIDHeaderMiddleware())
}
```

- **otelgin.Middleware**：为每个请求从 Header 中提取或新建 Trace，并**把 Span 和 Trace 信息放入 `c.Request.Context()`**。后续所有用 `c.Request.Context()` 的代码都会自动处于同一 Trace 下。
- **traceIDHeaderMiddleware**：把当前 Span 的 `TraceID` 写入响应头 `X-Trace-ID`，前端或日志可以用它去 Jaeger 里查整条链。

因此：**Handler 里务必使用 `c.Request.Context()` 往下传**，不要用 `context.Background()`，否则会断链。

### 3.3 数据库：GORM + otelgorm + context

`initialize/gorm.go` 中在启用 Tracing 时注册了 otelgorm 插件：

```go
if observability.TracerEnabled() {
    gormCfg.Plugins = map[string]gorm.Plugin{
        "otelgorm": otelgorm.NewPlugin(),
    }
}
```

只有用 **带 context 的 DB** 时，GORM 才会为每次查询创建子 Span。因此项目统一通过 `global.DB(ctx)` 取 DB：

```go
// global/global.go
func DB(ctx context.Context) *gorm.DB {
    if ctx == nil {
        return GVA_DB
    }
    return GVA_DB.WithContext(ctx)
}
```

在 Handler 里要写成：

```go
global.DB(ctx.Request.Context()).Find(&categories)
```

这样 Jaeger 里会看到：**HTTP Span → 若干条 GORM 子 Span（如 Find、First）**，每条 Span 对应一次 SQL。

### 3.4 Redis：redisotel

`initialize/redis.go` 中：

```go
if observability.TracerEnabled() {
    if err := redisotel.InstrumentTracing(client); err != nil { ... }
}
```

Redis 客户端被注入后，所有带 `ctx` 的调用（如 `client.Get(ctx, key)`）都会在当前 Trace 下生成 Redis 子 Span。因此 **Redis 调用也要传请求的 context**（例如 `c.Request.Context()`），而不是 `context.Background()`。

### 3.5 业务层手动打点（可选但推荐）

otelgin 只给 HTTP 打一个 Span；GORM/Redis 是“按调用”自动打点。如果希望链路上有**业务语义**（如「获取分类列表」「创建借阅」），可以在 Service 或 Handler 里手动创建子 Span：

```go
ctx, span := observability.StartSpan(ctx, "CategoryService.GetList")
defer span.End()
// ... 业务逻辑，所有 DB/Redis 调用都用 ctx
```

这样在 Jaeger 里会看到：**HTTP → CategoryService.GetList → 多条 GORM Span**，便于区分“时间花在哪个业务步骤”。

本项目在 `observability/tracing.go` 中提供了 `StartSpan(ctx, spanName)` 便捷方法；在 `api/v1/category.go` 的 `GetCategoryList` 中有示例用法。

## 四、Context 传递规范（重要）

链路能串起来的前提是 **同一个 context 从入口传到每一层**：


| 层级            | 正确做法                                                                    | 错误做法                        |
| ------------- | ----------------------------------------------------------------------- | --------------------------- |
| Handler       | 使用 `c.Request.Context()`，并传给 Service / DB                               | 使用 `context.Background()`   |
| Service       | 方法签名带 `ctx context.Context`，原样传给 DB、Redis、HTTP 客户端                      | 不传 ctx 或新建 context          |
| 定时任务 / Worker | 若需独立 Trace，可 `ctx, span := StartSpan(context.Background(), "Cron.XXX")` | 随意用 Background 会导致无法和上游请求关联 |


**记忆口诀**：**从 HTTP 进来就用 Request 的 Context，一路传到底。**

## 五、如何查看链路（Jaeger）

1. **本地**：用 Docker 起 Jaeger（支持 OTLP gRPC 4317），例如：
  ```bash
   docker run -d --name jaeger -p 16686:16686 -p 4317:4317 \
     jaegertracing/all-in-one:latest
  ```
2. 配置中保证 `tracing.enabled: true`、`tracing.endpoint: localhost:4317`。
3. 发起请求后，从响应头拿到 `X-Trace-ID`，在 Jaeger UI（[http://localhost:16686）中按](http://localhost:16686）中按) TraceID 搜索，即可看到该请求的完整 Span 树（HTTP、GORM、Redis、业务 Span）。

## 六、与日志、Metrics 的关系

- **Metrics**（如 `observability/metrics.go`）：聚合的 QPS、延迟分位、错误率，看整体健康度。
- **Tracing**：单次请求的完整路径和每步耗时，定位具体慢请求、错误请求。
- **日志**：若在结构化日志（如 zap）里带上 **trace_id**（以及 span_id），可以在 Kibana 里按 trace_id 查日志，在 Jaeger 里按 trace_id 查链路，两边互相关联。本项目在 `middleware/request_context.go` 中在记录请求日志时加入了 `trace_id`（当 Tracing 启用时），便于对照。

三者结合：**先看 Metrics 发现异常，再用 Tracing 按 TraceID 看调用链，用日志里的 trace_id 查同一请求的详细日志。**

## 七、小结


| 环节    | 本项目实现                                            | 你要记住的                     |
| ----- | ------------------------------------------------ | ------------------------- |
| 标准与导出 | OpenTelemetry + OTLP gRPC                        | 与具体后端解耦，可换 Jaeger/Tempo 等 |
| HTTP  | otelgin + X-Trace-ID 响应头                         | 入口用 `c.Request.Context()` |
| DB    | otelgorm + `global.DB(ctx)`                      | 所有 DB 调用都传 ctx            |
| Redis | redisotel                                        | Redis 调用也要传 ctx           |
| 业务语义  | `observability.StartSpan(ctx, "Service.Action")` | 关键业务步骤可手动打 span           |
| 日志    | 请求日志里带 trace_id                                  | 便于与 Jaeger 按 TraceID 关联   |


从「一次请求一个 Trace，各层用 Context 传递、自动或手动打 Span」出发，再扩展到多服务（通过 Propagator 在 HTTP/gRPC 间传递 Trace 信息），就是分布式链路追踪在本项目中的完整实践。
