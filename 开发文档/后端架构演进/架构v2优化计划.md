# 架构 v2 优化计划（方案 B 精简版）

基于 v1 增强型单体，向可扩展单体集群演进，适合毕设展示架构与工程能力。

---

## 1. 优先级与工作量

| 优先级 | 升级项 | 工作量 | 毕设展示点 | 状态 |
|--------|--------|--------|------------|------|
| P0 | API 多实例 + Nginx 负载均衡 | 1～2 天 | 无状态设计、水平扩展 | 已完成 |
| P1 | 分布式追踪（OpenTelemetry + Jaeger） | 1～2 天 | 可观测性、排障能力 | 已完成 |
| P2 | 限流与熔断 | 1 天 | 稳定性保障、防雪崩 |
| （可选） | MySQL 读写分离 | 2～3 天 | 读写分离、一致性权衡 |

---

## 2. P0：API 多实例 + Nginx 负载均衡

### 2.1 目标
- 证明 API 无状态、可水平扩展
- Nginx 做负载均衡，支持 2～3 个 API 实例

### 2.2 实施步骤
1. **Docker Compose**：将单实例 `api` 改为多实例（api1、api2、api3）或使用 `deploy.replicas` / `--scale`

2. **Nginx**：配置 `upstream`，对 `/api/*` 做轮询或加权负载均衡

3. **验证**：多实例启动后，请求应分散到不同 API 实例（可通过响应头或日志区分）

   ```bash
   ➜ for i in {1..6}; do curl -sI http://localhost/api/healthz | grep X-Instance-Id; done
   X-Instance-Id: api-3
   X-Instance-Id: api-1
   X-Instance-Id: api-2
   X-Instance-Id: api-3
   X-Instance-Id: api-1
   X-Instance-Id: api-2
   ```

   

### 2.3 毕设要点
- 架构图：多实例 + 负载均衡
- 压测对比：单实例 vs 多实例的 QPS、P99 延迟
- 无状态设计说明：Session 在 Redis、无本地内存状态

---

## 3. P1：分布式追踪（OpenTelemetry + Jaeger）

### 3.1 目标
- 每个请求贯穿 `trace_id`，可追踪 API → Redis → MySQL
- 在 Jaeger UI 中查看完整调用链

### 3.2 实施步骤
1. **OpenTelemetry SDK**：在 Gin 中接入，为每个请求生成 trace_id / span_id
2. **GORM/Redis 埋点**：在 DB 查询、Redis 调用处注入 context，传播 trace
3. **Jaeger**：docker-compose 增加 Jaeger 服务，接收 OTLP 数据
4. **响应头**：可选在响应中返回 `X-Trace-ID`，方便前端关联

### 3.3 毕设要点
- 可观测性三层：日志 + 指标 + 追踪
- 举例说明：如何用 trace_id 快速定位慢请求或错误链路

---

## 4. P2：限流与熔断

### 4.1 目标
- 全局限流：防止瞬时流量打垮服务
- 熔断：对 Redis/MySQL 调用失败做熔断，防止级联故障

### 4.2 实施步骤
1. **限流**：Nginx `limit_req_zone` 或 Go 层 token bucket / 滑动窗口
2. **熔断**：使用 `github.com/sony/gobreaker` 包裹 Redis、DB 调用

### 4.3 毕设要点
- 稳定性设计
- 如何防止雪崩、保护下游资源

---

## 5. 不建议在毕设阶段做的事

- 微服务拆分：改动大、与当前规模不匹配
- 引入 Kafka：已有 Redis Stream，足够
- K8s：Compose 足够，可仅在文档中展望

---

## 6. 实施顺序

```
P0 (必做) → P1 (推荐) → P2 (可选)
```

完成 P0 后，系统即可作为「可扩展单体」展示；P1、P2 根据时间择一或都做。
